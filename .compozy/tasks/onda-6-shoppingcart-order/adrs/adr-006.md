# ADR-006: Tax calculation at BFF — deferred remote in order-service

## Status

Accepted

## Date

2026-07-26

## Context

`OrderServiceImpl` uses `TaxService` in-process for `calculateShoppingCartTotal` and `processOrder`. `tax-service` (Onda 1) handles **admin CRUD** for tax classes/rates. Checkout tax computation may stay in monolith or move remote during Wave 6.

Moving tax into `order-service` adds another dependency during the highest-risk saga and duplicates address/product context already assembled in BFF checkout.

## Decision

For **Wave 6 Execute**:

- **Tax computation invoked from `CheckoutApplicationService`** via HTTP to `tax-service` (or in-process tax core if strangler not yet on tax — prefer HTTP per Onda 1 pattern)
- **`OrderSnapshot.taxItems`** carries pre-computed tax lines to `order-service` commit endpoint
- **`order-service` SHALL NOT** call `TaxService` or `tax-service` during commit or totals calculation

**Upgrade path (post-Wave 6):** Optional flag `wave6.tax.remote-in-order-service` to move totals tax logic into order-service if BFF latency unacceptable — requires new ADR.

## Alternatives considered

### Tax fully in order-service

- **Pros:** Order owns all totals logic.
- **Cons:** order-service needs shipping address, product tax class snapshots; extra HTTP round-trips from cart; higher saga complexity.
- **Rejected for Wave 6.**

### Tax remains in-process sm-core only

- **Pros:** Zero change.
- **Cons:** Blocks order-service extraction for totals endpoint.
- **Rejected** — totals must be in order-service (cycle break).

### Shared tax-library JAR

- **Pros:** No network.
- **Cons:** Couples order-service to tax rules JAR; violates extraction goal.
- **Rejected.**

## Consequences

**Positive:** Smaller order-service; BFF already has checkout context; tax-service reused.

**Negative:** BFF must stay in sync with tax rule changes; single point for tax bugs at checkout.
