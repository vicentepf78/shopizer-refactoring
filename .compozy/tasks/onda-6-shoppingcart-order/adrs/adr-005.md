# ADR-005: Hub OrderFacade decomposition strategy

## Status

Accepted

## Date

2026-07-26

## Context

The checkout hub (`OrderFacadeImpl` + bypass APIs) is identified as critical issue #2 in the master plan — MODEL + FUNCTIONAL coupling with 12 sm-core service injections. Two `OrderFacadeImpl` classes exist in different packages.

## Decision

Decompose in **three slices** (TLC T33–T36):

1. **Route bypass APIs** — `OrderPaymentApi`, `OrderTotalApi`, `OrderShippingApi` → `CheckoutApplicationService`
2. **Thin checkout methods** on `OrderFacadeImpl` — delegate to `CheckoutApplicationService`; remove `PaymentService`, `ShippingService`, `ProductService` from checkout code paths
3. **Read paths** — `OrderFacadeHttpAdapter` → order-service when `wave6.order.strangler.enabled`

Consolidate duplicate `OrderFacadeImpl` (v1 package) into single canonical facade (GAP-ORD-01).

**Target metric:** ≤ 4 sm-core injections referenced by checkout paths in `OrderFacadeImpl` (down from 12).

## Alternatives considered

### Delete OrderFacade entirely

- **Pros:** Maximum simplification.
- **Cons:** Breaks 20+ API injection sites; large blast radius.
- **Rejected** — thin facade preserves API contracts.

### Move all order logic to order-service including facades

- **Pros:** Clean service boundary.
- **Cons:** BFF still needs DTO mapping and resolver; duplicates shop-layer populators.
- **Rejected for Wave 6** — Strangler pattern keeps controllers in sm-shop.

## Consequences

**Positive:** Measurable hub reduction; bypass APIs unified; easier code review for new checkout features.

**Negative:** Large refactor touch surface — mitigated with characterization tests before edits.
