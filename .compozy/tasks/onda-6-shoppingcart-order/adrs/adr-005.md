# ADR-005: Estratégia de decomposição do hub OrderFacade

## Status

Aceito

## Data

2026-07-26

## Contexto

O hub de checkout (`OrderFacadeImpl` + bypass APIs) é identificado como issue crítica #2 no plano mestre — acoplamento MODEL + FUNCTIONAL com 12 injeções de serviços sm-core. Duas classes `OrderFacadeImpl` existem em pacotes diferentes.

## Decisão

Decompor em **três fatias** (TLC T33–T36):

1. **Rotear bypass APIs** — `OrderPaymentApi`, `OrderTotalApi`, `OrderShippingApi` → `CheckoutApplicationService`
2. **Métodos checkout finos** em `OrderFacadeImpl` — delegar a `CheckoutApplicationService`; remover `PaymentService`, `ShippingService`, `ProductService` dos caminhos de código checkout
3. **Caminhos read** — `OrderFacadeHttpAdapter` → order-service quando `wave6.order.strangler.enabled`

Consolidar `OrderFacadeImpl` duplicado (pacote v1) em facade canônica única (GAP-ORD-01).

**Métrica alvo:** ≤ 4 injeções sm-core referenciadas por caminhos checkout em `OrderFacadeImpl` (de 12).

## Alternativas consideradas

### Deletar OrderFacade inteiramente

- **Prós:** Máxima simplificação.
- **Contras:** Quebra 20+ sites de injeção API; blast radius grande.
- **Rejeitada** — facade fina preserva contratos API.

### Mover toda lógica order para order-service incluindo facades

- **Prós:** Fronteira de serviço limpa.
- **Contras:** BFF ainda precisa mapeamento DTO e resolver; duplica populators da camada shop.
- **Rejeitada na Onda 6** — padrão Strangler mantém controllers em sm-shop.

## Consequências

**Positivas:** Redução mensurável do hub; bypass APIs unificadas; code review mais fácil para novas features checkout.

**Negativas:** Superfície grande de refactor — mitigada com testes de caracterização antes das edições.
