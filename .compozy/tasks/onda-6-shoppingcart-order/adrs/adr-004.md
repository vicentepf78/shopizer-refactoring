# ADR-004: Transactional outbox para eventos do domínio order

## Status

Aceito

## Data

2026-07-26

## Contexto

Após commit da saga, ações downstream (templates de email, ajuste de inventário, analytics) não devem usar eventos Spring in-process que falham silenciosamente em restart de serviço. Notificação cross-service exige entrega confiável sem anomalias de dual-write.

## Decisão

Implementar **transactional outbox** em `order-service`:

- Tabela `ORDER_OUTBOX` no MySQL compartilhado
- Inserir linha no outbox na **mesma transação** da persistência de pedido
- Relay `@Scheduled` in-process (padrão) publica em `ApplicationEventPublisher` / futuro message bus
- Tipos de evento: `OrderPlaced`, `OrderPaid`, `OrderCancelled`

Caminho de upgrade do relay: extrair para worker standalone sem mudança de schema.

## Alternativas consideradas

### Change Data Capture (Debezium)

- **Prós:** Sem código de relay na aplicação.
- **Contras:** Complexidade de infra; não está no stack atual.
- **Adiado.**

### Fire-and-forget async após commit

- **Prós:** Simples.
- **Contras:** Eventos perdidos em crash entre commit e publish.
- **Rejeitada.**

### Dual-write para message queue

- **Prós:** Publish rápido.
- **Contras:** Inconsistente se escrita na fila falhar após commit no DB.
- **Rejeitada.**

## Consequências

**Positivas:** Entrega at-least-once; trilha de auditoria; alinha com PoC outbox da Onda 3.

**Negativas:** Lag do relay; monitorar profundidade do outbox (alerta > 100 pendentes).

## Notas de implementação

- Linhas com `published_at IS NULL` polled a cada 5s (configurável)
- DLQ após 10 falhas — script de replay manual no runbook
