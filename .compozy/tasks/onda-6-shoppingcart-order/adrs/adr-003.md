# ADR-003: Saga choreography for processOrder

## Status

Accepted

## Date

2026-07-26

## Context

`OrderServiceImpl.processOrder` runs payment, shipping, order persist, and cart clear under global AOP transaction (`TransactionalAspectAwareService`). This creates the **order↔payments cycle** (`PaymentServiceImpl` calls back to `OrderService`) and prevents runtime split.

Onda 3 delivers saga/outbox PoC on `processOrder` in the monolith. Onda 5 extracts stateless payment/shipping to `integration-service`.

## Decision

Replace monolithic `processOrder` with **saga choreography** orchestrated by `CheckoutApplicationService`:

- **No 2PC / XA** across services
- **Compensating transactions** on failure (cancel order, void payment per module, skip cart clear)
- **Feature flag** `wave6.checkout.saga.enabled` — `false` retains legacy in-process path

Order persistence and outbox write occur in **one local transaction** on order-service (step 3). Payment is a separate step (step 4) after order record exists.

## Alternatives considered

### Orchestration engine (Temporal/Camunda)

- **Pros:** Durable workflow engine.
- **Cons:** New dependency; team familiarity; overkill for single checkout flow.
- **Rejected** — ponytail: in-code saga with outbox; upgrade path documented.

### Keep global transaction, split DB later

- **Pros:** No behavior change.
- **Cons:** Cannot extract order/payments runtimes.
- **Rejected** — blocks Wave 6 goal.

### Choreography-only (no central orchestrator)

- **Pros:** Decentralized.
- **Cons:** Hard to reason about checkout; poor rollback UX.
- **Rejected** — BFF orchestrator required (ADR-002).

## Consequences

**Positive:** Breaks order↔payments cycle; enables independent deploy; testable compensation.

**Negative:** Eventual consistency window between order create and payment; requires idempotency (CHK-09).

**Risks:** Partial failure edge cases — mitigated with compensation tests (TLC T27, T59).
