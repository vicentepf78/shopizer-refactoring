# ADR-002: Checkout Application Service como fronteira do BFF

## Status

Aceito

## Data

2026-07-26

## Contexto

`OrderFacadeImpl` injeta 12 serviços sm-core mais `CustomerFacade` e `ShoppingCartFacade`. Bypass APIs (`OrderPaymentApi`, `OrderTotalApi`, `OrderShippingApi`) injetam serviços adicionais diretamente. Este hub não pode migrar para microserviços sem um ponto de entrada único de orquestração.

A Onda 3 introduz `CheckoutApplicationService` como application service local no monólito com snapshots DTO. A Onda 6 torna-o a **única fronteira de checkout** quando a saga está habilitada.

## Decisão

`CheckoutApplicationService` vive em **`sm-shop`** (pacote `com.salesmanager.shop.checkout`) e é dono de:

- Orquestração saga de place-order
- Cálculo de tax (chama tax-service)
- Orquestração payment/shipping (chama integration-service)
- Clear do carrinho após commit bem-sucedido
- Endpoints de totals/cotação de frete delegados das bypass APIs

`OrderFacadeImpl` delega operações de checkout a este serviço; operações de leitura delegam a `OrderFacadeHttpAdapter`.

## Alternativas consideradas

### Extrair checkout para `checkout-service`

- **Prós:** Fronteira microservice pura.
- **Contras:** Onda de maior risco adiciona terceiro deployable; BFF ainda precisa de resolver e contexto de sessão; dobra hops de rede em cada passo de checkout.
- **Rejeitada na Onda 6** (caminho de upgrade AD-024).

### Manter OrderFacadeImpl como hub com clientes HTTP

- **Prós:** Refactor menor.
- **Contras:** 12 injeções permanecem; orquestração não testável; viola requisitos HUB.
- **Rejeitada.**

## Consequências

**Positivas:** Saga testável; costura clara para extração futura; decomposição do hub mensurável (≤4 deps sm-core em caminhos de checkout).

**Negativas:** sm-shop cresce em responsabilidade; deve impedir novas injeções sm-core em facades (ArchUnit).
