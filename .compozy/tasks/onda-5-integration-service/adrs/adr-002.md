# ADR-002: Orquestração de pagamento stateless — sem ownership de Order

## Status

Aceito

## Data

2026-07-26

## Contexto

`PaymentServiceImpl.processPayment` chama `orderService.addOrderStatusHistory` e `orderService.saveOrUpdate(order)` após sucesso no gateway — metade funcional do **ciclo order ↔ payments** (plano mestre §6.5). A Onda 6 não pode extrair Order enquanto integration muta pedidos. A Onda 3 introduz checkout application service e fundação saga/outbox para ciclo de vida de pedido.

## Decisão

`integration-service` **NÃO DEVE** injetar `OrderService` nem escrever em tabelas `ORDERS` / histórico de status de pedido. APIs de pagamento aceitam `orderSnapshotId` e snapshots DTO; retornam `TransactionResult`. Transições de status de pedido permanecem no checkout application service / saga de `sm-shop` após receber o resultado da transação. Registros `Transaction` PODEM ser persistidos em DB compartilhado por integration-service.

## Alternativas consideradas

### Alternativa 1: integration-service dono de atualizações de Order via callback HTTP ao monólito

- **Prós:** Centraliza lógica pós-pagamento.
- **Contras:** Reintroduz ciclo via HTTP; saga já é dona da orquestração no design Onda 3.
- **Rejeitada:** Saga de checkout é a dona correta da orquestração.

### Alternativa 2: Dual-write na transição (integration atualiza Order quando strangler off)

- **Prós:** Migração gradual.
- **Contras:** Prolonga ciclo; dois caminhos de código divergem.
- **Rejeitada:** Flag Strangler limita caminho legado apenas à janela de rollback; caminho novo é stateless desde o dia um.

### Alternativa 3: Integration somente por eventos (sem API sync de pagamento)

- **Prós:** Máximo desacoplamento.
- **Contras:** UX de checkout exige resposta síncrona de pagamento hoje; outbox sozinha insuficiente para fluxo authorize/capture.
- **Rejeitada:** API interna síncrona com fronteira stateless é o split mínimo correto.

## Consequências

### Positivas

- Quebra ciclo sm-core para Onda 6.
- Fronteira de confiança clara: integration = gateways + transações; checkout = estado do pedido.

### Negativas

- Saga de checkout deve tratar compensação de falha (reembolso) — depende do design saga Onda 3.
- Fluxo em duas etapas (pagamento depois atualização de pedido) exige chaves de idempotência na saga.

### Riscos

- Regressão se caminho legado `PaymentServiceImpl` ainda escreve pedidos com strangler habilitado — mitigado por teste gate T24.

## Notas de implementação

- API interna: `POST /internal/v1/payments/process`
- `PaymentProcessRequest.orderSnapshotId` obrigatório
- ArchUnit ou grep CI: sem `OrderService` em `sm-integration-core` / `integration-service`
