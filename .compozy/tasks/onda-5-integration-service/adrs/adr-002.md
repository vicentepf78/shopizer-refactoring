# ADR-002: Stateless payment orchestration — no Order entity ownership

## Status

Accepted

## Date

2026-07-26

## Context

`PaymentServiceImpl.processPayment` calls `orderService.addOrderStatusHistory` and `orderService.saveOrUpdate(order)` after gateway success — the functional half of the **order ↔ payments cycle** (master plan §6.5). Wave 6 cannot extract Order while integration mutates orders. Wave 3 introduces checkout application service and saga/outbox foundation for order lifecycle.

## Decision

`integration-service` **MUST NOT** inject `OrderService` or write to `ORDERS` / order status history tables. Payment APIs accept `orderSnapshotId` and snapshot DTOs; they return `TransactionResult`. Order status transitions remain in `sm-shop` checkout application service / saga after receiving the transaction result. `Transaction` records MAY be persisted in shared DB by integration-service.

## Alternatives considered

### Alternative 1: Integration-service owns Order updates via HTTP callback to monolith

- **Pros:** Centralizes post-payment logic.
- **Cons:** Reintroduces cycle via HTTP; saga already owns orchestration in Wave 3 design.
- **Rejected:** Checkout saga is the correct orchestration owner.

### Alternative 2: Dual-write during transition (integration updates Order when strangler off)

- **Pros:** Gradual migration.
- **Cons:** Prolongs cycle; two code paths diverge.
- **Rejected:** Strangler flag gates old path only for rollback window; new path is stateless from day one.

### Alternative 3: Event-only integration (no sync payment API)

- **Pros:** Maximum decoupling.
- **Cons:** Checkout UX requires synchronous payment response today; outbox alone insufficient for authorize/capture flow.
- **Rejected:** Sync internal API with stateless boundary is minimal correct split.

## Consequences

### Positive

- Breaks sm-core cycle for Wave 6.
- Clear trust boundary: integration = gateways + transactions; checkout = order state.

### Negative

- Checkout saga must handle failure compensation (refund) — depends on Onda 3 saga design.
- Two-step flow (payment then order update) requires idempotency keys in saga.

### Risks

- Regression if legacy `PaymentServiceImpl` path still writes orders when strangler enabled — mitigated by T24 gate test.

## Implementation notes

- Internal API: `POST /internal/v1/payments/process`
- `PaymentProcessRequest.orderSnapshotId` required
- ArchUnit or CI grep: no `OrderService` in `sm-integration-core` / `integration-service`
