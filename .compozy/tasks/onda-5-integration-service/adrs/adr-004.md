# ADR-004: PaymentModuleV2 and ShippingQuoteModuleV2 contracts from Onda 3

## Status

Accepted

## Date

2026-07-26

## Context

Current `PaymentModule` and `ShippingQuoteModule` in `sm-core-modules` accept JPA entities (`Order`, `Customer`, `ShoppingCartItem`, `MerchantStore`) — MODEL coupling disguised as plugins (master plan §6.7). Onda 3 delivers DTO-based V2 contracts and snapshots (`OrderSnapshot`, `CustomerSnapshot`, etc.) without deploying new microservices.

## Decision

Wave 5 **depends on Onda 3 deliverables** `PaymentModuleV2` and `ShippingQuoteModuleV2` in `sm-core-modules`, plus snapshot DTOs in `shopizer-api-contracts`. `integration-service` invokes V2 interfaces at runtime. Legacy V1 plugins are bridged via `PaymentModuleV2Adapter` / `ShippingQuoteModuleV2Adapter` (ponytail: remove when all plugins implement V2 natively).

## Alternatives considered

### Alternative 1: Redesign contracts inside Wave 5

- **Pros:** Self-contained wave.
- **Cons:** Duplicates Onda 3 scope; master plan explicitly assigns contract redesign to Wave 3.
- **Rejected:** Prerequisite ordering is fixed.

### Alternative 2: Keep V1 entity contracts in integration-service

- **Pros:** Less adapter code.
- **Cons:** Forces `sm-core-model` and Order graph into integration-service; fails stateless goal.
- **Rejected:** Contradicts decomposition strategy.

### Alternative 3: OpenAPI-only contracts without sm-core-modules update

- **Pros:** HTTP-first plugins.
- **Cons:** Breaks Maven Central publishable module pattern; 8+ Java plugin implementations in-repo.
- **Rejected:** In-process registry (ADR-005) requires Java interfaces.

## Consequences

### Positive

- Wave 5 Execute blocked until contracts exist — forces correct sequencing.
- Publishable `sm-core-modules` remains integration boundary for external payment starters.

### Negative

- Adapter maintenance until plugins migrated.
- Onda 3 delay directly blocks Wave 5 calendar.
