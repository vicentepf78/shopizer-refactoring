# ADR-006: APIs de checkout permanecem no BFF com checkout application service

## Status

Aceito

## Data

2026-07-26

## Contexto

`OrderPaymentApi` injeta cinco serviços sm-core mais facades — hub de checkout contornando facades (plano mestre §6.6). `OrderShippingApi` compõe de forma similar cart, pricing e frete. Mover esses controllers para integration-service empurraria montagem de cart/order para bounded context errado.

A Onda 3 introduz **Checkout Application Service** no monólito para orquestrar passos de checkout e saga.

## Decisão

`OrderPaymentApi` e `OrderShippingApi` **permanecem em `sm-shop`**. Delegam a `CheckoutApplicationService` (pagamento) e facades cart/catálogo (frete), que chamam APIs HTTP de `IntegrationServiceClient`. integration-service expõe rotas admin de config e APIs de operação `/internal/v1/**` — não caminhos de checkout da vitrine.

## Alternativas consideradas

### Alternativa 1: Mover OrderPaymentApi para integration-service

- **Prós:** Menos hops para pagamento.
- **Contras:** Serviço de integration precisa montagem cart/order/customer; viola fronteira stateless de pedido.
- **Rejeitada.**

### Alternativa 2: Novo microsserviço checkout-service na Onda 5

- **Prós:** Dono de orquestração limpo.
- **Contras:** Explosão de escopo; checkout service é entregável monólito Onda 3, não deployable Onda 5.
- **Rejeitada.**

### Alternativa 3: Browser direto → integration-service para pagamento

- **Prós:** Redução de latência.
- **Contras:** Quebra caminhos REST congelados (STR-06); expõe superfície interna.
- **Rejeitada.**

## Consequências

### Positivas

- BFF retém orquestração de checkout; integration permanece provedor de capability genérica.
- Alinha com Strangler Fig — mesmas URLs, nova delegação de backend.

### Negativas

- Hop HTTP extra para pagamento — aceitável dentro do orçamento de latência 2×.
