# ADR-006: Checkout APIs remain on BFF with checkout application service

## Status

Accepted

## Date

2026-07-26

## Context

`OrderPaymentApi` injects five sm-core services plus facades — a checkout hub bypassing facades (master plan §6.6). `OrderShippingApi` similarly composes cart, pricing, and shipping. Moving these controllers to integration-service would push cart/order assembly into the wrong bounded context.

Onda 3 introduces **Checkout Application Service** in the monolith to orchestrate checkout steps and saga.

## Decision

`OrderPaymentApi` and `OrderShippingApi` **remain in `sm-shop`**. They delegate to `CheckoutApplicationService` (payment) and cart/catalog facades (shipping), which call `IntegrationServiceClient` HTTP APIs. Integration-service exposes admin config routes and `/internal/v1/**` operation APIs — not storefront checkout paths.

## Alternatives considered

### Alternative 1: Move OrderPaymentApi to integration-service

- **Pros:** Fewer hops for payment.
- **Cons:** Integration service needs cart/order/customer assembly; violates stateless order boundary.
- **Rejected.**

### Alternative 2: New checkout-service microservice in Wave 5

- **Pros:** Clean orchestration owner.
- **Cons:** Scope explosion; checkout service is Onda 3 monolith deliverable, not Wave 5 deployable.
- **Rejected.**

### Alternative 3: Direct browser → integration-service for payment

- **Pros:** Latency reduction.
- **Cons:** Breaks frozen REST paths (STR-06); exposes internal surface.
- **Rejected.**

## Consequences

### Positive

- BFF retains checkout orchestration; integration stays generic capability provider.
- Aligns with Strangler Fig — same URLs, new backend delegation.

### Negative

- Extra HTTP hop for payment — acceptable within 2× latency budget.
