# ADR-005: Registry de plugins in-process em integration-service

## Status

Aceito

## Data

2026-07-26

## Contexto

Shopizer usa registry Spring `Map<String, PaymentModule>` (`ModulesConfiguration`, bean `paymentModules`) com implementações como JARs/classes no classpath (`StripePayment`, `UPSShippingQuote`, etc.). Starters externos (ex.: Canada Post) publicam contratos `sm-core-modules`. Hipótese original "Integration Hub cedo" foi **rejeitada** na análise de acoplamento por questões de contrato + ciclo order — Onda 5 trata contratos primeiro, depois extrai orquestração.

## Decisão

Manter o **registry de plugins in-process** dentro de `integration-service` (e `sm-integration-core`). Plugins permanecem beans Java carregados de `sm-integration-core` / dependências starter opcionais — **não** microsserviços separados por gateway. `ModulesConfiguration` move com os orquestradores.

## Alternativas consideradas

### Alternativa 1: Um microsserviço por provedor de pagamento

- **Prós:** Escala independente por gateway.
- **Contras:** Explosão operacional; config compartilhada; sem demanda de negócio na escala Shopizer.
- **Rejeitada:** YAGNI.

### Alternativa 2: Funções serverless por plugin

- **Prós:** Isolamento.
- **Contras:** Nova plataforma; reescrever todos os plugins; fora da stack (monólito Java 11).
- **Rejeitada.**

### Alternativa 3: Deixar plugins no monólito; extrair só API de config

- **Prós:** Onda 5 menor.
- **Contras:** Chamadas gateway ainda in-process; ciclo permanece para `processPayment`.
- **Rejeitada:** Falha nos objetivos PAY-07..PAY-12.

## Consequências

### Positivas

- Reutiliza padrão comprovado; mudança mínima de código de plugin além do adaptador V2.
- Unidade implantável única para todos os gateways — operações mais simples.

### Negativas

- JAR de integration-service inclui todos os plugins — artefato maior.
- Falha de plugin pode afetar serviço inteiro — aceitável para volatilidade baixa do subdomínio genérico (poucos commits em pagamentos).
