# ADR-005: In-process plugin registry inside integration-service

## Status

Accepted

## Date

2026-07-26

## Context

Shopizer uses a Spring `Map<String, PaymentModule>` registry (`ModulesConfiguration`, `paymentModules` bean) with implementations as classpath JARs/classes (`StripePayment`, `UPSShippingQuote`, etc.). External starters (e.g. Canada Post) publish `sm-core-modules` contracts. Original "Integration Hub early" hypothesis was **rejected** in coupling analysis because of contract + order cycle issues — Wave 5 addresses contracts first, then extracts orchestration.

## Decision

Keep the **in-process plugin registry** inside `integration-service` (and `sm-integration-core`). Plugins remain Java beans loaded from `sm-integration-core` / optional starter dependencies — **not** separate microservices per gateway. `ModulesConfiguration` moves with orchestrators.

## Alternatives considered

### Alternative 1: One microservice per payment provider

- **Pros:** Independent scaling per gateway.
- **Cons:** Operational explosion; shared config; no business demand in Shopizer scale.
- **Rejected:** YAGNI.

### Alternative 2: Serverless functions per plugin

- **Pros:** Isolation.
- **Cons:** New platform; rewrite all plugins; out of stack (Java 11 monolith).
- **Rejected.**

### Alternative 3: Leave plugins in monolith; only config API extracts

- **Pros:** Smaller Wave 5.
- **Cons:** Gateway calls still in-process; cycle remains for `processPayment`.
- **Rejected:** Fails PAY-07..PAY-12 goals.

## Consequences

### Positive

- Reuses proven pattern; minimal plugin code change beyond V2 adapter.
- Single deployable unit for all gateways — simpler operations.

### Negative

- integration-service JAR includes all plugins — larger artifact.
- Plugin failure can affect whole service — acceptable for generic subdomain volatility (low commits on payments).
