# ADR-003: Shared MySQL for integration configuration and transactions

## Status

Accepted

## Date

2026-07-26

## Context

Waves 1–2 inherited AD-003: runtime extraction with **shared schema** `SALESMANAGER` to avoid blocking on database split. Payment and shipping configuration lives in `MERCHANT_CONFIGURATION`; transactions in `TRANSACTION`. `integration-service` needs read/write access to these tables.

## Decision

`integration-service` uses the **same MySQL database** as the monolith for integration configuration and transaction persistence. No database-per-service split in Wave 5. Schema ownership is documented; coordinated migrations if columns change. Order tables remain read-prohibited (ADR-002).

## Alternatives considered

### Alternative 1: Dedicated integration database with sync

- **Pros:** Stronger isolation.
- **Cons:** Dual-write or replication complexity; breaks Strangler rollback; high effort for generic subdomain.
- **Rejected:** Violates AD-003 without approved architectural decision.

### Alternative 2: Configuration only in integration DB; transactions in monolith

- **Pros:** Smaller integration DB surface.
- **Cons:** Payment queries still couple monolith to transaction storage; partial extraction.
- **Rejected:** Orchestration owns transaction persistence today.

### Alternative 3: Stateless integration — no DB at all

- **Pros:** Pure stateless microservice.
- **Cons:** Merchant module config and transaction audit trail require persistence; plugins expect `MerchantConfigurationService`.
- **Rejected:** Configuration CRUD is in-scope P1.

## Consequences

### Positive

- Fastest path to deployable service; matches Waves 1–2 operations model.
- Existing encryption and `MerchantConfigurationService` patterns reusable.

### Negative

- Schema coupling remains until future DB split wave.
- Connection pool contention possible — monitor in Wave 6.

### Risks

- Accidental JPA entity scan pulling Order entities — mitigated by package-scoped entity scan in Boot app.
