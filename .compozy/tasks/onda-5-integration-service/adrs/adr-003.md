# ADR-003: MySQL compartilhado para configuração e transações de integration

## Status

Aceito

## Data

2026-07-26

## Contexto

Ondas 1–2 herdaram AD-003: extração de runtime com schema **compartilhado** `SALESMANAGER` para não bloquear no split de banco. Configuração de pagamento e frete vive em `MERCHANT_CONFIGURATION`; transações em `TRANSACTION`. `integration-service` precisa de acesso leitura/escrita a essas tabelas.

## Decisão

`integration-service` usa o **mesmo banco MySQL** do monólito para configuração de integration e persistência de transações. Sem split database-per-service na Onda 5. Ownership de schema documentado; migrações coordenadas se colunas mudarem. Tabelas de Order permanecem proibidas para escrita (ADR-002).

## Alternativas consideradas

### Alternativa 1: Banco dedicado de integration com sync

- **Prós:** Isolamento mais forte.
- **Contras:** Complexidade de dual-write ou replicação; quebra rollback Strangler; alto esforço para subdomínio genérico.
- **Rejeitada:** Viola AD-003 sem decisão arquitetural aprovada.

### Alternativa 2: Config apenas em DB de integration; transações no monólito

- **Prós:** Superfície menor de DB de integration.
- **Contras:** Queries de pagamento ainda acoplam monólito ao armazenamento de transações; extração parcial.
- **Rejeitada:** Orquestração é dona da persistência de transações hoje.

### Alternativa 3: integration stateless — sem DB

- **Prós:** Microsserviço puramente stateless.
- **Contras:** Config de módulo merchant e trilha de auditoria de transação exigem persistência; plugins esperam `MerchantConfigurationService`.
- **Rejeitada:** CRUD de config está no escopo P1.

## Consequências

### Positivas

- Caminho mais rápido para serviço implantável; combina com modelo operacional Ondas 1–2.
- Padrões existentes de criptografia e `MerchantConfigurationService` reutilizáveis.

### Negativas

- Acoplamento de schema permanece até onda futura de split de DB.
- Contenção de connection pool possível — monitorar na Onda 6.

### Riscos

- Entity scan JPA acidental puxando entidades Order — mitigado por entity scan com escopo de pacote no app Boot.
