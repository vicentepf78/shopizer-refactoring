# ADR-001: Wave 3 as monolith-only contracts wave (no new services)

## Status

Accepted

## Date

2026-07-26

## Context

The master plan places Wave 3 (weeks 33–38) between service extractions (Waves 1–2) and catalog/customer extraction (Wave 4). Wave 3 deliverables — snapshots, integration DTOs, checkout application service, outbox foundation — are **prerequisites** for Waves 4–6, not standalone deployable domains. Deploying empty or stub microservices would add operational cost without user-facing value.

Waves 1 and 2 established the pattern: extract when a bounded context has clear REST surfaces and independent runtime value. Wave 3 work is almost entirely **compile-time and in-process** boundary cleanup.

## Decision

Execute Wave 3 as a **single Compozy workflow** (`onda-3-contracts-dto`) with **zero new Spring Boot applications**, **zero new Docker Compose services**, and **no Strangler HTTP adapters**. All code changes land in existing modules: `shopizer-api-contracts`, `sm-core-modules`, `sm-core`, `sm-shop`, `sm-shop-model`, and test updates in `search-service` for contract migration only.

## Alternatives considered

### Alternative 1: Deploy a `contracts-service` or `checkout-service` early

- **Pros:** Visible milestone; rehearse Wave 6 topology.
- **Cons:** Checkout still needs monolith catalog/cart/tax in-process; premature network boundary adds latency and dual-write risk without saga complete.
- **Rejected:** Violates master plan "SEM extração de serviços" for Wave 3.

### Alternative 2: Defer Wave 3 until catalog extraction (Wave 4)

- **Pros:** Fewer monolith touch points at once.
- **Cons:** Search and integration remain blocked; `ProductIndexPayload` interim becomes permanent; B-001/B-002 fester.
- **Rejected:** Master plan explicitly sequences contracts before catalog read.

### Alternative 3: Three separate workflows (snapshots, checkout, integration)

- **Pros:** Smaller PRs.
- **Cons:** Shared tenant types and snapshot builders create merge conflicts; one gate is simpler for a refactoring wave.
- **Rejected:** Single workflow with parallel TLC tracks (like Wave 2) is sufficient.

## Consequences

### Positive

- Smaller operational footprint; CI gate is `./mvnw clean install` only.
- Focuses review on contract quality and checkout behavior parity.
- Clear handoff artifact for Wave 4 Specify.

### Negative

- Less visible "demo" than Waves 1–2; success is measured by gates and blocker closure.
- Large monolith diff risk — mitigated by feature flags and phased facade migration.

## Implementation notes

- No `wave3.*.base-url` properties.
- Update `.specs/project/STATE.md` on completion, not `docker-compose-wave3.yml`.
