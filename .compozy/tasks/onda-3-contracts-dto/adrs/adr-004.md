# ADR-004: PaymentModuleV2 / ShippingQuoteModuleV2 paralelos com bridge adapter legacy

## Status

Aceito

## Data

2026-07-26

## Contexto

`PaymentModule` e `ShippingQuoteModule` em `sm-core-modules` aceitam entidades JPA (`Order`, `Customer`, `MerchantStore`, `ShoppingCartItem`, `Delivery`, etc.). Isso é acoplamento MODEL disfarçado de API de plugin (plano mestre §6.7). A extração de integration-service na Onda 5 exige contratos apenas DTO.

Plugins existentes (Stripe, PayPal, USPS, etc.) implementam a interface legacy e estão em `sm-core` como classes compiladas. Quebrar compatibilidade binária forçaria reescrever todas as integrações na Onda 3 — fora de escopo.

## Decisão

1. Adicionar **DTOs de integração** em `sm-core-modules` (ex.: `PaymentRequestContext`, `PaymentCaptureContext`, `ShippingQuoteRequestContext`, `IntegrationStoreContext`) — sem tipos JPA.
2. Introduzir interfaces **`PaymentModuleV2`** e **`ShippingQuoteModuleV2`** usando apenas DTOs + tipos `IntegrationConfiguration` / `IntegrationModule` existentes.
3. **`PaymentServiceImpl` / `ShippingServiceImpl`** detectam plugins capazes de V2 via `instanceof` ou flag opcional de registry; caso contrário **adaptam** grafo entidade → DTO → chamam V2, ou delegam a métodos legacy `PaymentModule`.
4. **Sem rewrites de plugin** na Onda 3; fornecer **adapter de referência** `LegacyPaymentModuleBridge` que implementa V2 delegando a V1 (para testes).
5. Onda 5 move plugins para processo remoto; Onda 3 apenas prova caminho DTO in-process.

## Alternativas consideradas

### Alternativa 1: Mudar PaymentModule in-place

- **Rejeitada:** Quebra todos os plugins; alto risco.

### Alternativa 2: Novo módulo `sm-integration-contracts` separado de sm-core-modules

- **Rejeitada:** YAGNI — estender JAR `sm-core-modules` publicável existente.

### Alternativa 3: API de plugin apenas JSON

- **Rejeitada:** Over-engineering para Onda 3; interfaces Java batem com padrão registry existente.

## Consequências

### Positivas

- Fronteira de extração clara para Onda 5.
- Plugins legacy inalterados.
- Mapeamento DTO centralizado na camada de serviço uma vez.

### Negativas

- Duas hierarquias de interface até legacy deprecado.
- Código adapter mapping deve ficar em sync com mudanças do modelo de entidade.

## Notas de implementação

- DTOs usam `MerchantStoreId` / money como `BigDecimal` / IDs não refs de entidade.
- `validateModuleConfiguration` aceita `IntegrationStoreContext` em V2.
