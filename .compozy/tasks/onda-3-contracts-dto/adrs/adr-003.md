# ADR-003: Phased facade migration to MerchantStoreId and LanguageCode

## Status

Accepted

## Date

2026-07-26

## Context

Blocker B-001: 20+ facade interfaces in `sm-shop-model` pass `MerchantStore` and `Language` JPA entities. `AbstractDataPopulator` hard-wires the same types. ~450 call sites use `MerchantStoreArgumentResolver`. A big-bang replacement would touch most of `sm-shop` and risk Wave 2 regressions.

Wave 3 must **start** the migration without completing all 76 facades — catalog and customer facades are Wave 4 scope.

## Decision

1. Introduce **`MerchantStoreId`** (store code string wrapper) and **`LanguageCode`** (ISO code wrapper) in `shopizer-api-contracts`.
2. **Phase 1 (Wave 3):** Migrate signatures on checkout-adjacent and search facades:
   - `OrderFacade`, `ShoppingCartFacade`, `SearchFacade`, `ShippingFacade`
   - `CategoryFacade`, `ProductCommonFacade` (read paths used by checkout/search)
3. Provide **`TenantEntityBridge`** in `sm-shop` (or `sm-core`) to hydrate entities from codes for in-process service calls — **not** in contracts JAR.
4. Add **overload** on `AbstractDataPopulator`: `populate(source, MerchantStoreId storeId, LanguageCode lang)` defaulting to bridge hydration.
5. **Phase 2–3 (Waves 4–6):** Remaining facades per published migration plan (`FAC-06`).
6. **`MerchantStoreArgumentResolver` unchanged** in Wave 3 — still resolves entity for controllers; facades receive converted value types at boundary.

## Alternatives considered

### Alternative 1: Big-bang all 76 facades

- **Rejected:** Unbounded diff; blocks Wave 3 timebox.

### Alternative 2: Only new methods; keep entity methods forever

- **Rejected:** Perpetuates B-001; doubles API surface.

### Alternative 3: String codes without value types

- **Rejected:** Primitive obsession; no validation; easy to swap store/lang argument order.

## Consequences

### Positive

- P1 checkout path is entity-free at facade **interface** boundary.
- HTTP adapters in Wave 4+ pass codes naturally.
- Incremental compile fixes per facade.

### Negative

- Temporary bridge layer and dual populator overloads.
- Some internal code still hydrates entities — document as technical debt until Wave 6.

## Implementation notes

- Value types: immutable, `equals`/`hashCode` on code, `toString` for logs.
- ArchUnit test (Wave 3 tail): new facade methods must not add `MerchantStore` parameters.
