# ADR-005: Local transactional outbox for processOrder (no broker in Wave 3)

## Status

Accepted

## Date

2026-07-26

## Context

`OrderServiceImpl.processOrder` runs payment, customer create, order persist, transaction records, and inventory decrement in one `@Transactional` method. `PaymentServiceImpl` calls back into `OrderService` — a bidirectional cycle (master plan issue #1). Wave 6 needs to split order and payments across processes.

A full distributed saga with message broker (Kafka/RabbitMQ) is not justified in Wave 3: no second service consumes events yet. However, doing nothing leaves no seam for Wave 6.

## Decision

1. Add **`CHECKOUT_OUTBOX`** table in shared schema with columns: `id`, `aggregate_id` (order id or correlation uuid), `event_type`, `payload` (JSON), `status`, `created_at`, `processed_at`.
2. Refactor `processOrder` into **named stages** inside `CheckoutApplicationService` / `OrderServiceImpl`:
   - `PAYMENT_REQUESTED` → `PAYMENT_CONFIRMED` → `ORDER_PERSISTED` → `INVENTORY_DECREMENTED`
3. Each stage writes an outbox row **in the same DB transaction** as the business mutation (transactional outbox pattern, local dispatcher only).
4. **In-process dispatcher** (scheduled or inline after commit) marks rows processed — no external broker.
5. Feature flag **`checkout.outbox.enabled`** default `false`; legacy single-method path preserved when disabled.
6. **No retry across JVMs** in Wave 3 — dispatcher is best-effort in monolith.

## Alternatives considered

### Alternative 1: Introduce Kafka now

- **Rejected:** YAGNI; operational cost; no consumer service.

### Alternative 2: Full saga orchestrator framework

- **Rejected:** Over-engineering; Spring state machine or Temporal deferred.

### Alternative 3: Only extract CheckoutApplicationService without outbox

- **Rejected:** Misses master plan saga/outbox deliverable; Wave 6 would re-touch same method.

## Consequences

### Positive

- Wave 6 can attach remote payment worker reading outbox or swap dispatcher for broker.
- Observable stages for debugging checkout failures.
- Feature flag enables safe rollout.

### Negative

- New table and migration script in shared DB.
- Dual code paths until flag default flips (Wave 6).

## Implementation notes

- Payload JSON uses `OrderSnapshot` / transaction ids — not full entity graphs.
- Idempotency key: `event_type` + `aggregate_id` + stage sequence.
- ponytail: global lock on dispatcher is acceptable for Wave 3; partition by store if throughput issues.
