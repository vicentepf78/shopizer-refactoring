# ADR-005: Outbox transacional local para processOrder (sem broker na Onda 3)

## Status

Aceito

## Data

2026-07-26

## Contexto

`OrderServiceImpl.processOrder` executa pagamento, criação de customer, persistência de order, registros de transação e decremento de inventário em um método `@Transactional`. `PaymentServiceImpl` chama de volta `OrderService` — um ciclo bidirecional (issue #1 do plano mestre). A Onda 6 precisa separar order e payments através de processos.

Uma saga distribuída completa com message broker (Kafka/RabbitMQ) não é justificada na Onda 3: ainda não há segundo serviço consumindo eventos. Porém, não fazer nada deixa sem seam para a Onda 6.

## Decisão

1. Adicionar tabela **`CHECKOUT_OUTBOX`** em schema compartilhado com colunas: `id`, `aggregate_id` (order id ou uuid de correlação), `event_type`, `payload` (JSON), `status`, `created_at`, `processed_at`.
2. Refatorar `processOrder` em **estágios nomeados** dentro de `CheckoutApplicationService` / `OrderServiceImpl`:
   - `PAYMENT_REQUESTED` → `PAYMENT_CONFIRMED` → `ORDER_PERSISTED` → `INVENTORY_DECREMENTED`
3. Cada estágio escreve uma linha outbox **na mesma transação DB** que a mutação de negócio (padrão transactional outbox, dispatcher local apenas).
4. **Dispatcher in-process** (agendado ou inline após commit) marca linhas processadas — sem broker externo.
5. Feature flag **`checkout.outbox.enabled`** default `false`; caminho legacy de método único preservado quando desabilitado.
6. **Sem retry entre JVMs** na Onda 3 — dispatcher é best-effort no monólito.

## Alternativas consideradas

### Alternativa 1: Introduzir Kafka agora

- **Rejeitada:** YAGNI; custo operacional; sem serviço consumidor.

### Alternativa 2: Framework orquestrador saga completo

- **Rejeitada:** Over-engineering; Spring state machine ou Temporal adiado.

### Alternativa 3: Apenas extrair CheckoutApplicationService sem outbox

- **Rejeitada:** Perde entregável saga/outbox do plano mestre; Onda 6 re-tocaria o mesmo método.

## Consequências

### Positivas

- Onda 6 pode anexar worker payment remoto lendo outbox ou trocar dispatcher por broker.
- Estágios observáveis para debug de falhas de checkout.
- Feature flag permite rollout seguro.

### Negativas

- Nova tabela e script de migração em DB compartilhado.
- Caminhos de código duplos até flag default virar (Onda 6).

## Notas de implementação

- Payload JSON usa `OrderSnapshot` / ids de transação — não grafos completos de entidade.
- Chave de idempotência: `event_type` + `aggregate_id` + sequência de estágio.
- ponytail: global lock no dispatcher é aceitável para Onda 3; particionar por store se throughput exigir.
