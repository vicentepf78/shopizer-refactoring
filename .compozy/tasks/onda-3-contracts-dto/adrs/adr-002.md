# ADR-002: ProductSnapshot substitui ProductIndexPayload com evolução de schema

## Status

Aceito

## Data

2026-07-26

## Contexto

A Onda 2 introduziu `ProductIndexPayload` (AD-009) como DTO de índice interim para que `search-service` rodasse sem JPA. O design OQ-06 adiou a migração de `SearchItem` para a Onda 3. O plano mestre lista `ProductSnapshot` como entregável da Onda 3 para search, leitura de catálogo e leituras cross-service.

`ProductIndexPayload` usa `Map<String,String>` soltas para variants/inventory. Um `ProductSnapshot` mais rico pode servir indexação de search, APIs futuras de leitura de catálogo e payloads de evento sem três formas paralelas.

## Decisão

1. Adicionar **`ProductSnapshot`** em `shopizer-api-contracts` como projeção canônica de leitura de catálogo.
2. **`ProductIndexPayload` permanece** para compatibilidade retroativa da API HTTP de índice, mas vira uma **projeção fina** de `ProductSnapshot` (builder produz snapshot primeiro, depois mapea para payload).
3. Bump do **`schemaVersion` default para 2** em payloads de índice quando campos snapshot são populados; `search-service` aceita v1 e v2 durante a transição.
4. **`ProductIndexPayloadBuilder`** (monólito) refatorado para construir `ProductSnapshot` internamente.

## Alternativas consideradas

### Alternativa 1: Renomear ProductIndexPayload para ProductSnapshot in-place

- **Prós:** Um nome de tipo.
- **Contras:** Quebra Pact da Onda 2 e consumidores search-service implantados imediatamente.
- **Rejeitada:** Preferir evolução aditiva.

### Alternativa 2: Manter ProductIndexPayload para sempre; adicionar ProductSnapshot separado

- **Prós:** Zero mudança na API de índice.
- **Contras:** Manutenção duplicada de campos; viola DRY para leitura de catálogo na Onda 4.
- **Rejeitada:** Snapshot canônico único com adapter para payload legacy.

### Alternativa 3: Stream de eventos CQRS completo agora

- **Prós:** Future-proof para Kafka.
- **Contras:** YAGNI — sem broker na Onda 3 (sibling ADR-005).
- **Rejeitada:** Apenas DTO snapshot; eventos reutilizam serialização snapshot depois.

## Consequências

### Positivas

- Um caminho de builder de JPA `Product` → snapshot → consumidores index/search/catálogo.
- Fecha débito técnico AD-009 incrementalmente.
- Pact pode versionar em `schemaVersion`.

### Negativas

- Tipos duplos temporários no pacote contracts até Onda 4 deprecar caminho apenas-payload.
- search-service deve lidar com documentos v1 já indexados.

## Notas de implementação

- Package: `com.salesmanager.contracts.catalog.ProductSnapshot`
- Não importar JPA em contracts; tipos aninhados são DTOs simples (`ProductSnapshotVariant`, etc.).
- Mappers MapStruct em `sm-shop` ou `sm-core`.
