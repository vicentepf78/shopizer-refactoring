# ADR-007: Product images via content-service (complete Onda 2 deferral)

## Status

Accepted

## Date

2026-07-26

## Context

Onda 2 design OQ-02 deferred `productFileManager` and `/static/products/**` to catalog wave (`.specs/features/onda-2-content-search-merchant/context.md`). Content-service owns CMS blobs; catalog owns product metadata. Product option/variant images currently flow through monolith facades calling in-process CMS managers.

Wave 4 touches catalog boundaries and is the natural place to complete blob integration without putting binary storage in catalog-service.

## Decision

- **Product/variant/option image uploads** use existing `ContentServiceClient` (Wave 2) from monolith write facades (`ProductOptionFacadeImpl`, `ProductVariantGroupFacadeImpl`, etc.).
- **content-service** gains endpoints or extends internal APIs for `FileContentType` PRODUCT / VARIANT / PROPERTY if not already sufficient from Wave 2 P2 stubs.
- **catalog-service** returns image **URLs** in read DTOs only — does not store blobs.
- **Static serving** follows Wave 2 `StaticContentProxy` pattern; extend for `/static/products/**` if required.

## Alternatives considered

### Alternative 1: catalog-service owns product blobs

- **Pros:** Colocate metadata + images.
- **Cons:** Reintroduces split-brain opposite of content wave; duplicates CMS backends.
- **Rejected.**

### Alternative 2: Defer again to Onda 5+

- **Pros:** Smaller Wave 4.
- **Cons:** Leaves known deferral unpaid; admin image flows still in-process CMS.
- **Rejected:** P2 scope acceptable.

## Consequences

### Positive

- Consistent blob ownership in content-service.
- catalog-service stays JPA + DTO focused.

### Negative

- Extra HTTP hops on admin image upload.
- content-service scope grows slightly.

### Risks

- Partial upload failures — reuse AD-014 compensate patterns where applicable.
