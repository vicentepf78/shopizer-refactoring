# ADR-007: Imagens de produto via content-service (completar adiamento da Onda 2)

## Status

Aceito

## Data

2026-07-26

## Contexto

O design da Onda 2 OQ-02 adiou `productFileManager` e `/static/products/**` para a onda de catálogo (`.specs/features/onda-2-content-search-merchant/context.md`). Content-service possui blobs CMS; catalog possui metadados de produto. Imagens de opção/variante de produto atualmente fluem por facades do monólito chamando managers CMS in-process.

A Onda 4 toca fronteiras de catálogo e é o lugar natural para completar integração de blobs sem colocar armazenamento binário no catalog-service.

## Decisão

- **Uploads de imagens de produto/variante/opção** usam `ContentServiceClient` existente (Onda 2) a partir de facades de write do monólito (`ProductOptionFacadeImpl`, `ProductVariantGroupFacadeImpl`, etc.).
- **content-service** ganha endpoints ou estende APIs internas para `FileContentType` PRODUCT / VARIANT / PROPERTY se stubs da Onda 2 P2 forem insuficientes.
- **catalog-service** retorna **URLs** de imagem em DTOs de leitura apenas — não armazena blobs.
- **Serving estático** segue padrão `StaticContentProxy` da Onda 2; estender para `/static/products/**` se necessário.

## Alternativas consideradas

### Alternativa 1: catalog-service possui blobs de produto

- **Prós:** Colocaliza metadados + imagens.
- **Contras:** Reintroduz split-brain oposto à onda de content; duplica backends CMS.
- **Rejeitada.**

### Alternativa 2: Adiar novamente para Onda 5+

- **Prós:** Onda 4 menor.
- **Contras:** Deixa adiamento conhecido não pago; fluxos admin de imagem ainda em CMS in-process.
- **Rejeitada:** Escopo P2 aceitável.

## Consequências

### Positivas

- Ownership de blobs consistente no content-service.
- catalog-service permanece focado em JPA + DTO.

### Negativas

- Hops HTTP extras no upload admin de imagem.
- Escopo do content-service cresce levemente.

### Riscos

- Falhas de upload parcial — reutilizar padrões de compensação AD-014 onde aplicável.
