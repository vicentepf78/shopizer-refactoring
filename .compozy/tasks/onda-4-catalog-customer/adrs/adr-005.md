# ADR-005: Cart merge via CustomerSnapshot orchestrated in monolith

## Status

Accepted

## Date

2026-07-26

## Context

Master plan Wave 4 customer scope: "After CustomerSnapshot; decouple merge with cart." Today `CustomerFacadeImpl` and `ShoppingCartServiceImpl.mergeShoppingCarts` use in-process `Customer` entities, often in the same database transaction as cart rows. Extracting `customer-service` without addressing merge would either force distributed transactions or break login UX.

Customer service layer is relatively isolated (5/10), but cart merge is the critical cross-cutting flow.

## Decision

- **`customer-service`** exposes `GET /internal/v1/customers/{id}/snapshot` returning `CustomerSnapshot`.
- **`CustomerServiceClient.getSnapshot(customerId, storeCode)`** used by monolith on login.
- **`ShoppingCartService.mergeShoppingCarts`** refactored to accept snapshot or primitive customer id — **no HTTP call inside** shopping cart service.
- **Cart persistence remains monolith** until Onda 6; no `shoppingcart-service` in Wave 4.

## Alternatives considered

### Alternative 1: Extract shoppingcart-service with customer-service

- **Pros:** Complete checkout-adjacent extraction.
- **Cons:** Cart↔order cycle; master plan Onda 6.
- **Rejected.**

### Alternative 2: customer-service participates in merge transaction (2PC)

- **Pros:** Strong consistency.
- **Cons:** No 2PC infra; violates lazy/YAGNI principle.
- **Rejected.**

### Alternative 3: Event-driven merge after login

- **Pros:** Async decoupling.
- **Cons:** UX delay; race conditions on checkout.
- **Rejected:** Synchronous merge required today.

## Consequences

### Positive

- customer-service deployable without cart DB ownership.
- Clear trust boundary: snapshot is integration contract.

### Negative

- Monolith still owns merge complexity.
- Extra HTTP round-trip on login when strangler enabled.

### Risks

- customer-service down blocks merge — mitigated by fail-closed with clear error (Design).
