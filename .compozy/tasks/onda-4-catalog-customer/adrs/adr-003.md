# ADR-003: ProductSnapshot as canonical cross-service product contract

## Status

Accepted

## Date

2026-07-26

## Context

Onda 2 introduced interim `ProductIndexPayload` (schemaVersion 1) to extract search before full product contracts (STATE.md AD-009). Onda 3 delivers `ProductSnapshot` as the systemic DTO for cross-service product reads. Wave 4 catalog extraction and search indexing should converge on **one contract** to avoid dual builders and pact drift.

## Decision

- **`ProductSnapshot` schemaVersion 2** is the canonical product integration DTO in `shopizer-api-contracts`.
- `catalog-service` exposes internal HTTP snapshot API returning v2.
- Monolith `ProductSnapshotBuilder` replaces `ProductIndexPayloadBuilder` for search indexing.
- `search-service` accepts v2; v1 supported temporarily during migration, then deprecated.

## Alternatives considered

### Alternative 1: Keep ProductIndexPayload forever

- **Pros:** No migration work.
- **Cons:** Duplicates Wave 3 investment; catalog-service and search diverge.
- **Rejected:** Onda 3 prerequisite explicitly delivers ProductSnapshot.

### Alternative 2: catalog-service builds snapshots only via JPA graph internally

- **Pros:** Single builder location.
- **Cons:** Monolith still needs snapshots for events when writes stay local; couples indexing to catalog-service uptime.
- **Rejected:** Monolith builder remains for write-side events; optional HTTP snapshot for verification.

### Alternative 3: Event bus with Avro schemas

- **Pros:** Industry standard at scale.
- **Cons:** No bus infra in project; YAGNI for Wave 4.
- **Rejected:** HTTP + RestTemplate pattern (AD-005).

## Consequences

### Positive

- Unifies search index and catalog read contract.
- Enables future order/shipping modules to consume same snapshot.

### Negative

- Migration task for producer and search-service.
- v1/v2 dual support window increases test matrix.

### Risks

- Field drift between ReadableProduct and ProductSnapshot — mitigated by pact and shared builder tests.
