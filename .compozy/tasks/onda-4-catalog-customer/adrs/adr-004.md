# ADR-004: Módulos thin sm-catalog-core e sm-customer-core

## Status

Aceito

## Data

2026-07-26

## Contexto

A Onda 2 introduziu `sm-content-core` e `sm-merchant-core` para extrair subconjuntos de domínio sem puxar todo o `sm-core` para cada serviço Boot (STATE.md AD-011). Catalog tem 22 implementações de serviço; customer tem 7. Copy-paste em módulos Boot bifurcaria lógica; depender de `sm-core` completo a partir de `catalog-service` arrastaria dependências de order/payment.

## Decisão

Criar **`sm-catalog-core`** (subconjunto read de catálogo + repositories + mappers) e **`sm-customer-core`** (serviços customer, optin, attribute + repositories). Serviços Boot dependem de thin cores + `shopizer-api-contracts`. `sm-core` delega caminhos de leitura para thin cores enquanto retém código write/admin até ondas posteriores.

## Alternativas consideradas

### Alternativa 1: catalog-service depende de sm-core completo

- **Prós:** Menos trabalho de extração.
- **Contras:** Dependências transitivas massivas; derrota propósito da decomposição.
- **Rejeitada.**

### Alternativa 2: Duplicar serviços apenas em módulos Boot

- **Prós:** Sem novos módulos Maven.
- **Contras:** Bifurcação de lógica; manutenção dupla.
- **Rejeitada.**

### Alternativa 3: sm-commerce-core único para catalog+customer

- **Prós:** Um JAR intermediário.
- **Contras:** Mescla bounded contexts; perde benefícios de isolamento de customer.
- **Rejeitada:** Cores separadas por domínio.

## Consequências

### Positivas

- Corresponde ao padrão comprovado da Onda 2.
- Habilita gates de teste independentes por core.
- search-service permanece livre de sm-core (inalterado).

### Negativas

- Dois novos módulos Maven para manter.
- Superfície de API cuidadosa para evitar deps circulares sm-core ↔ thin core.

### Riscos

- Split read/write incompleto em serviços — mitigado por checklist explícito de migração de métodos no TLC T6/T15.

## Notas de implementação

- Registrar módulos no `pom.xml` raiz.
- JaCoCo verify nos cores (T32).
