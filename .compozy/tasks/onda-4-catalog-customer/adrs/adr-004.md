# ADR-004: Thin sm-catalog-core and sm-customer-core modules

## Status

Accepted

## Date

2026-07-26

## Context

Onda 2 introduced `sm-content-core` and `sm-merchant-core` to extract domain subsets without pulling the entire `sm-core` into every Boot service (STATE.md AD-011). Catalog has 22 service implementations; customer has 7. Copy-paste into Boot modules would fork logic; depending on full `sm-core` from `catalog-service` would drag order/payment dependencies.

## Decision

Create **`sm-catalog-core`** (read catalog subset + repositories + mappers) and **`sm-customer-core`** (customer, optin, attribute services + repositories). Boot services depend on thin cores + `shopizer-api-contracts`. `sm-core` delegates read paths to thin cores while retaining write/admin code until later waves.

## Alternatives considered

### Alternative 1: catalog-service depends on full sm-core

- **Pros:** Less extraction work.
- **Cons:** Massive transitive deps; defeats decomposition purpose.
- **Rejected.**

### Alternative 2: Duplicate services into Boot modules only

- **Pros:** No new Maven modules.
- **Cons:** Logic fork; double maintenance.
- **Rejected.**

### Alternative 3: Single sm-commerce-core for catalog+customer

- **Pros:** One intermediate JAR.
- **Cons:** Merges bounded contexts; customer isolation score benefits lost.
- **Rejected:** Separate cores per domain.

## Consequences

### Positive

- Matches proven Onda 2 pattern.
- Enables independent test gates per core.
- search-service remains free of sm-core (unchanged).

### Negative

- Two new Maven modules to maintain.
- Careful API surface to avoid circular deps sm-core ↔ thin core.

### Risks

- Incomplete read/write split in services — mitigated by explicit method migration checklist in TLC T6/T15.

## Implementation notes

- Register modules in root `pom.xml`.
- JaCoCo verify on cores (T32).
