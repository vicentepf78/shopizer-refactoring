# ADR-006: Admin catalog writes remain in monolith for Wave 4

## Status

Accepted

## Date

2026-07-26

## Context

ADR-002 establishes read-only catalog service boundary. Admin UI and private REST APIs (`POST/PUT/DELETE` product, variant, inventory mutations) currently run through `sm-shop` controllers into `sm-core` write services with AOP events (`PublishProductAspect`) for search indexing.

Routing writes to catalog-service in Wave 4 would require dual maintenance of write logic, distributed transaction concerns, and content-service image orchestration before the write graph is understood as a single bounded context operation.

## Decision

For Wave 4:

- Private admin product APIs **always execute in-process** in the monolith.
- Strangler HTTP adapters apply **only to read methods** on product/category facades.
- Search indexing after writes uses monolith-side `ProductSnapshotBuilder` + HTTP producer to search-service (unchanged producer location from Onda 2, upgraded contract).

## Alternatives considered

### Alternative 1: CQRS with catalog-service write API behind feature flag

- **Pros:** Progressive write migration.
- **Cons:** Highest risk item in wave; doubles API surface.
- **Deferred:** Future wave after order decoupling.

### Alternative 2: BFF proxies admin writes to catalog-service

- **Pros:** Single write owner.
- **Cons:** Same as full write extraction without benefits of local transaction with content/images.
- **Rejected for Wave 4.**

## Consequences

### Positive

- Smallest write-path diff; admin UX unchanged.
- Clear documentation for operators: catalog-service is read scale-out.

### Negative

- catalog-service cannot run greenfield admin standalone.
- Continued MODEL coupling for admin in monolith (expected).

## Implementation notes

- ArchUnit / wiring test T30 proves no HTTP delegation on write routes.
- Document in operator runbook.
