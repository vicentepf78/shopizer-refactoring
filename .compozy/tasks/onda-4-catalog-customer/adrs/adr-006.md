# ADR-006: Writes admin de catálogo permanecem no monólito na Onda 4

## Status

Aceito

## Data

2026-07-26

## Contexto

ADR-002 estabelece fronteira read-only do serviço de catálogo. Admin UI e APIs REST privadas (`POST/PUT/DELETE` de produto, variante, mutações de inventário) atualmente rodam por controllers `sm-shop` em serviços de write `sm-core` com eventos AOP (`PublishProductAspect`) para indexação de busca.

Rotear writes para catalog-service na Onda 4 exigiria manutenção dual de lógica de write, preocupações de transação distribuída e orquestração de imagens content-service antes que o grafo de write seja entendido como operação de bounded context único.

## Decisão

Para a Onda 4:

- APIs admin privadas de produto **sempre executam in-process** no monólito.
- Adaptadores HTTP Strangler aplicam **somente a métodos de leitura** em facades product/category.
- Indexação de busca após writes usa `ProductSnapshotBuilder` no lado monólito + producer HTTP para search-service (localização do producer inalterada da Onda 2, contrato atualizado).

## Alternativas consideradas

### Alternativa 1: CQRS com API write do catalog-service atrás de feature flag

- **Prós:** Migração progressiva de write.
- **Contras:** Item de maior risco na onda; dobra superfície de API.
- **Adiado:** Onda futura após desacoplamento de order.

### Alternativa 2: BFF faz proxy de writes admin para catalog-service

- **Prós:** Dono único de write.
- **Contras:** Mesmo que extração write completa sem benefícios de transação local com content/images.
- **Rejeitada para Onda 4.**

## Consequências

### Positivas

- Menor diff no caminho de write; UX admin inalterada.
- Documentação clara para operadores: catalog-service é scale-out de leitura.

### Negativas

- catalog-service não pode rodar admin greenfield standalone.
- Acoplamento MODEL continuado para admin no monólito (esperado).

## Notas de implementação

- Teste ArchUnit / wiring T30 prova ausência de delegação HTTP em rotas de write.
- Documentar no runbook de operador.
