# ADR-002: Extração read-only de catálogo primeiro (CQRS faseado)

## Status

Aceito

## Data

2026-07-26

## Contexto

Catalog é o **domínio upstream principal** em `sm-core` com **10 referências de serviço inbound** (order, cart, shipping, search, merchant, reference e outros). Extração CRUD completa replicaria todo o grafo de write de catálogo — incluindo inventário, pricing, imagens, variantes e eventos de busca — através de uma fronteira de rede enquanto admin e jobs batch ainda precisam de consistência transacional com o monólito.

O plano mestre declara: "API read-heavy primeiro; write permanece no monólito temporariamente."

## Decisão

`catalog-service` possui **APIs GET públicas de vitrine** mais leituras internas de `ProductSnapshot`. **Todas as mutações admin privadas de produto** (POST/PUT/DELETE nas APIs admin de produto) permanecem em `sm-shop` / `sm-core` na Onda 4. Thin core `sm-catalog-core` extrai **somente serviços de leitura e mappers**.

## Alternativas consideradas

### Alternativa 1: Extração CRUD completa de catálogo

- **Prós:** Dono único do domínio de catálogo.
- **Contras:** Maior acoplamento; risco de dual-write; bloqueia em orquestração order/cart/inventory.
- **Rejeitada:** Score 7/10; aferente 10.

### Alternativa 2: Extrair apenas categorias (fatia menor)

- **Prós:** Menor risco.
- **Contras:** Leituras de produto são o tráfego principal; validação incompleta de ProductSnapshot.
- **Rejeitada:** Valor insuficiente; leitura de produto é o objetivo principal.

### Alternativa 3: Apenas read replicas / DB views

- **Prós:** Sem extração de serviço.
- **Contras:** Não valida padrão Strangler para catálogo; não implanta runtime independente.
- **Rejeitada:** Não atende objetivos da onda.

## Consequências

### Positivas

- Reduz raio de explosão da Onda 4.
- Caminho de escala de vitrine independente do caminho de write admin.
- Prepara extração futura de write com contrato de snapshot já no lugar.

### Negativas

- Split brain: monólito escreve linhas DB que catalog-service lê (aceitável com schema compartilhado AD-022).
- Dois caminhos de código para lógica de produto até migração de write.

### Riscos

- Leituras stale após write admin — mitigado por DB compartilhado + cache TTL curto opcional; índice de busca via producer de snapshot.

## Notas de implementação

- Requisito AD-020 aplicado em testes de wiring Strangler (T30).
- Métodos private de admin `ProductApi` nunca delegam HTTP.
